# SoulDrive 京东 AI + 移动存储大赛线上面试报告

> 使用场景：5 分钟项目介绍 + 面试追问准备  
> 项目定位：面向私有资产的端侧知识引擎  
> 建议赛道表达：技术能力组为主，兼顾产品创意价值  
> 核心一句话：SoulDrive 把移动存储从“文件容器”升级为“随身、离线、可审计的 AI 知识工作区”。

## 一、面试表达假设

1. 面试官关注的不只是“用了大模型”，而是 AI 与移动存储设备结合后，是否形成真实场景、真实闭环和可落地工程。
2. 5 分钟介绍不要铺太多代码细节，要按“痛点 -> 方案 -> 技术闭环 -> 亮点 -> 价值与展望”推进。
3. 项目当前最适合主打技术能力组：本地 RAG、移动工作区、安全加密、桌面 sidecar、证据链与审计都已有工程实现。

## 二、5 分钟正式演讲稿

### 0:00-0:35 开场：先把项目说准

各位老师好，我的项目叫 SoulDrive。我想解决的问题是：大量学习资料、论文和企业文档放在移动硬盘或 U 盘里时，通常只是“被动存储”。用户要查找、理解、总结资料，仍然要手动翻文件，甚至复制到云端工具，效率低，也有隐私风险。

SoulDrive 的目标，是把移动存储设备升级成一个随身的端侧 AI 知识引擎：资料留在本地，用户可以直接提问，并获得带证据来源的回答。

### 0:35-1:25 场景价值：为什么适合 AI + 移动存储

这个项目与本次“AI + 移动存储场景融合”的主题非常契合。移动存储的传统价值是容量和便携，但下一阶段更重要的是“带着知识和智能一起移动”。

例如学生可以把课程资料、论文和实验记录放在移动盘中，插入电脑后形成个人知识库；科研或企业用户可以把私有文档留在本地设备里，不上传云端，也能完成问答、总结、溯源和导图整理。这样，移动存储就从数据搬运工具变成可随身携带的 AI 工作区。

### 1:25-2:25 系统架构：讲清整体闭环

SoulDrive 采用桌面端加本地 sidecar 的架构。前端是 React + Tauri 桌面应用，负责文档管理、聊天、证据卡片和导图展示；后端是 Python 本地服务，负责解析、索引、RAG、安全和审计。

文档导入工作区后，系统会用 Docling 做版面感知解析，再建立向量索引、关键词索引、父子切片索引和轻量知识图谱。用户提问时，系统先从本地资料中召回证据，再用本地 GGUF 大模型生成答案。回答中会标注 E1、E2 这样的证据编号，前端还能展示证据来源和知识导图。

也就是说，它的闭环是：移动存储承载资料，本地引擎理解资料，本地模型生成答案，证据链保证回答可追溯。

### 2:25-3:35 技术亮点：突出差异化

这个项目我最想突出四个技术点。

第一是端侧和私有化。模型、索引、图谱和审计日志都优先放在本地工作区，不依赖把资料上传到云端。

第二是检索质量。项目没有只做简单向量检索，而是组合向量召回、FTS 关键词召回、父子切片、RRF 排序、reranker 和图谱补强，兼顾语义、关键词和实体关系。

第三是可信回答。生成前有 evidence gate，证据不足会拒答或降级；正常回答必须带引用编号，让用户看到“答案从哪里来”。

第四是移动存储工程化。桌面端会拉起本地 sidecar，使用随机端口和 API token；移动工作区拔出后，系统进入 locked 状态，避免继续访问已经不在场的数据。

### 3:35-4:25 工程完成度：让面试官相信可落地

从工程实现上看，SoulDrive 不是只停留在概念层的作品。它有明确的工作区目录规范，支持 `SoulDrive/` 作为移动盘业务工作区；有加密文档存储和密钥管理；有独立索引 worker，避免 PDF 解析阻塞主服务；也有 hash-chain 审计日志，可以检测审计记录是否被篡改。

项目还包含 40 多个测试文件，覆盖工作区、加密、API 安全、检索、RAG、图谱、审计和模型运行。这说明我不仅关注演示效果，也关注端侧产品上线时的稳定性、安全性和可维护性。

### 4:25-5:00 收束：愿景和比赛亮点

如果用一句话总结，SoulDrive 想做的是“移动存储设备上的个人 AI 知识操作系统”。它把大模型能力、端侧隐私、本地知识库和移动存储的便携性结合起来，让存储设备从保存文件，进一步变成理解文件和组织知识的入口。

后续我会继续优化端侧推理速度、更多文档类型和多模态资料支持，并把证据链、知识图谱和导图做成更自然的学习与办公工作流。谢谢各位老师。

## 四、建议展示顺序

1. 先展示桌面端主界面：让面试官看到它是完整产品，不只是命令行脚本。
2. 展示工作区状态：强调移动存储插入、运行态解锁、文档库和索引状态。
3. 导入或展示已有文档：说明文档进入后会解析、切片、索引。
4. 输入一个面向文档的问题：例如“总结这篇论文的核心贡献，并指出依据来自哪些章节”。
5. 展示回答中的证据编号、证据卡片和导图：重点讲“可信”和“可追溯”。
6. 最后展示审计或诊断区域：说明这不是普通聊天助手，而是面向私有资料的可信知识系统。

## 五、模型升级评测数据

这组数据建议在面试中作为“工程验证”使用，表达重点不是 7B 一定在所有指标上完胜，而是你已经建立了可复现实验链路，并能用数据指导模型选择。

| 指标 | 3B | 7B | 变化 |
| --- | ---: | ---: | ---: |
| 综合可靠率 | 53.5% | 61.4% | +7.9 个百分点 |
| 可回答题达标率 | 57.6% | 60.9% | +3.3 个百分点 |
| 拒答正确率 | 11.1% | 66.7% | +55.6 个百分点 |
| 拒答漏放率 | 88.9% | 33.3% | -55.6 个百分点 |
| 误拒率 | 0.0% | 3.3% | +3.3 个百分点 |
| 引用合法率 | 100.0% | 100.0% | 持平 |
| 答案关键词覆盖率 | 62.3% | 63.0% | +0.7 个百分点 |
| 平均端到端耗时 | 21977 ms | 29621 ms | +7644 ms |

建议讲法：从 3B 切换到 7B 后，综合可靠率从 53.5% 提升到 61.4%，最明显的是拒答正确率从 11.1% 提升到 66.7%，说明 7B 对“证据不足时不要乱答”的判断更稳；代价是平均端到端耗时增加约 7.6 秒。这个结果支持我后续做“双模型策略”：快速场景用 3B，关键问答或高可信模式用 7B。

这部分建议放在 PPT 的倒数第二页，用来回答“这个项目后续怎么继续做”。不要只说“优化性能、优化体验”，要体现你知道端侧 AI 产品的真实瓶颈。

| 阶段 | 优化方向 | 面试表达 |
| --- | --- | --- |
| 短期 | 性能与模型策略 | 基于 3B/7B 评测结果做双模型模式：快速问答优先 3B，高可信或复杂问题切换 7B；继续优化模型加载、上下文长度和首 token 延迟。 |
| 中期 | 文档与多模态扩展 | 从论文/PDF 扩展到 Word、PPT、图片 OCR、扫描件和音视频摘要，让移动工作区覆盖更真实的学习与办公资料。 |
| 中期 | 检索与证据质量 | 引入更细粒度的章节识别、表格理解、跨文档证据聚合和引用覆盖率评测，让回答更稳定、更可追溯。 |
| 长期 | 私有知识工作流 | 把问答、证据链、知识图谱、导图和审计打通，形成“导入资料 -> 理解资料 -> 组织知识 -> 输出报告”的完整工作流。 |
| 长期 | 设备级产品化 | 围绕移动存储做授权、加密、离线升级、模型包管理和低配设备适配，让它更接近可以交付的端侧产品。 |

建议讲法：未来我会围绕三条线继续做。第一是“更快”，用双模型策略平衡 3B 的速度和 7B 的可靠性；第二是“更广”，支持更多文档类型和 OCR/多模态资料；第三是“更像产品”，把证据链、知识图谱、导图、审计和移动工作区安全能力做成一条完整的私有知识工作流。

## 七、面试官可能追问与建议回答

### 1. 你和普通 RAG 项目的区别是什么？

普通 RAG 往往只解决“把文档问答跑通”。SoulDrive 更强调移动存储场景下的完整产品闭环：文档在移动工作区，索引和模型在本地，API 有安全边界，回答有证据链，运行过程有审计。它不是单点算法 Demo，而是把移动存储设备变成可携带的 AI 知识工作区。

### 2. 为什么要做端侧，而不是直接接云端大模型？

因为项目面对的是私有资料场景。很多论文笔记、企业资料、合同、实验记录不适合上传云端。端侧方案的优势是隐私边界清楚、离线可用、与移动存储天然结合。当然端侧也有挑战，比如模型体积、推理速度和硬件差异，所以项目里做了本地模型配置、GPU 检测和 CPU fallback。

### 3. 检索为什么不用单纯向量库？

单纯向量检索对语义相似问题有效，但对专有名词、编号、章节标题、公式缩写和中文关键词有时不稳定。SoulDrive 采用混合检索：向量负责语义，FTS 负责关键词，父子切片负责“短块召回、长块回答”，图谱负责实体关系补充，最后再融合排序。这能提升复杂文档问答的稳定性。

### 4. 你怎么控制大模型幻觉？

我做了两层控制。第一层是生成前的 evidence gate，如果证据数量或置信度不够，系统会拒答或降级。第二层是生成后的引用校验，回答需要带 E1、E2 这样的证据编号，前端会展示对应来源。我的目标不是让模型“永远都回答”，而是让它在证据不足时知道停下来。

### 5. 移动存储设备拔出会怎样？

系统会进入 locked 状态，停止继续访问工作区数据。移动工作区不是一个普通路径，而是系统运行态的一部分。这个设计把“数据是否在场”变成产品安全边界：设备在，知识引擎可用；设备不在，系统锁定。

### 6. 项目最大的难点是什么？

最大的难点不是某一个算法，而是端侧系统的工程闭环。包括文档解析质量、索引增量更新、模型推理资源、前后端通信、安全解锁、审计记录和移动盘路径变化。我的做法是把它拆成清晰模块：workspace 管路径和状态，indexer 管入库，knowledge_base 管检索，RAGEngine 管生成，Tauri 管桌面进程。

### 7. 如果继续参赛迭代，你最想优化什么？

我会分三层优化。短期先做性能和模型策略，利用 3B/7B 评测结果形成“双模型模式”：普通问题走更快的 3B，高可信或复杂问题切到 7B。中期扩展 Word、PPT、OCR、扫描件和多模态资料，让移动工作区覆盖更真实的资料形态。长期把问答、证据链、知识图谱、导图和审计打通，形成一条从导入资料到输出报告的私有知识工作流。

## 八、30 秒极简版

SoulDrive 是一个面向移动存储的端侧 AI 知识引擎。它让用户把论文、资料和私有文档放在移动盘里，插入电脑后自动形成本地知识库，并通过本地大模型进行问答、总结、证据溯源和导图整理。它的亮点是本地私有化、混合检索、证据链防幻觉、移动工作区锁定和 hash-chain 审计。我的目标是让移动存储从“文件容器”变成“随身 AI 知识工作区”。

## 九、面试当天提醒

1. 不要一开始就讲技术栈，先讲场景痛点和比赛契合度。
2. 讲技术时只抓四个词：端侧、混合检索、证据、安全。
3. 避免说“完全解决幻觉”，建议说“通过证据门槛和引用校验降低幻觉风险”。
4. 避免把项目说成纯论文助手，应该说“论文是当前演示入口，底层面向私有知识文档”。
5. 结尾一定回到移动存储价值：容量之外，下一代移动存储可以承载智能、知识和可信工作流。
