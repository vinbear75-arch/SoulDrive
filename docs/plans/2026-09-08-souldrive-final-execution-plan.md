# SoulDrive 最终优化执行大纲：先完成一个可验收的本机业务流程

日期：2026-09-08。用途：最终范围取舍、实施拆分与验收依据。

本文件替代前两版大纲的执行优先级；前两版保留为候选需求资料。这里的“最终”指计划审核完成，不表示缺陷已经修复或整机已经达到发布标准。本轮只新增本文件，没有修改功能代码、模型、评测数据或用户工作区。

## 1. 最终判断与交付范围

SoulDrive 已有项目空间、资料摄取与检索、实验账本、屏幕/语音输入、声明式 Skill、任务日志和 PPT 生成基础。下一步最有价值的工作，是使这些已有能力在一个真实流程中可靠衔接。

首轮目标固定为：**本机选择项目资料 → 找到可定位证据 → 比较符合条件的实验 → 审阅实际 PPT 大纲 → 确认生成 → 找回结果；发生中断或取消时，状态与实际行为一致。**

这符合仓库 `docs/product_b1_corpus_and_baseline.md` 所定义的长期研发项目业务。论文是资料来源之一，配置、指标、日志、截图和决策记录也属于业务核心。首轮验收优先使用已有明确证据的文本/指标材料，截图理解另列诊断，不把尚未验证的视觉能力作为主流程的必经条件。

### 1.1 相比 V2 的必要收缩

| V2 建议 | 最终取舍 | 原因 |
| --- | --- | --- |
| S0–S3 整体作为首个稳定版本 | 改为下述 E0–E7 的受限交付 | 原范围同时覆盖检索、报告、依赖传播、恢复和多模态，无法作为一轮小步优化兑现 |

| 重复统计补两个版本字段 | 先明确“同条件重复”与“条件变化比较”的区别 | 现有测试甚至将不同配置的运行合并；只补数据集/脚本门仍不充分 |
| 项目任务中心、通用中断恢复 | 首轮只完善 PPT 的确认、步骤间停止和恢复 | 索引、模型推理与 PPT 的停止机制不同，不能用一个按钮代表都可取消 |
| 报告、产物依赖、局部更新 | 后续按需立项 | 新增内容模型、依赖判断和编辑冲突，非现有 PPT 服务的小改动 |

| 多模态与推理性能全面优化 | 先定位三条既有 PNG 失败及真实计时边界 | 当前证据不足以承诺换模型后有收益或达到固定秒数 |

对标优秀产品的实际要求是：资料范围清楚、任务状态可信、结果能核对、失败能继续。首轮无需新增模型、Agent 框架、图数据库、向量数据库或观测平台。若某个修复必须引入这些依赖，应先重新解释其必要性，而不是自动扩大本计划。

## 3. 执行顺序与工作量边界

S 表示局部修改和针对性测试；M 表示跨后端、接口、持久化或 UI 的联动。它们是变更面判断，不是固定工期。E0 完成后再依据当前失败项和打包条件估算时间。

| 顺序 | 工作项 | 规模 | 依赖 | 退出交付物 |
| --- | --- | --- | --- | --- |
| E0 | 当前基线与五个缺口复现 | S | 无 | 当前清单、反例清单、验证记录 |
| E1 | 开发与发行解锁隔离 | S–M | E0 | 两条启动分支检查、实际发行形态验证 |
| E2 | 摘要范围与选取修正 | S–M | E0 | 摘要/归档/注入契约及长会话回归 |
| E3 | 重复统计兼容性 | S–M | E0，统计契约明确 | 不可比原因、同条件统计与差异比较分离 |
| E4 | PPT 实际大纲确认 | M | E0 | 持久化计划、确认、生成与重启流程 |
| E5 | PPT 步骤间停止与恢复 | M | E4 状态/任务契约确定 | 请求停止到终态的行为记录与竞争测试 |
| E6 | PNG 失败与计时诊断 | S–M，限诊断 | E0 | 三项失败分类和阶段计时；是否修复另作选择 |
| E7 | 一个项目完整验收与候选包 | M | E1–E5；E6 已说明边界 | 可复核演示、当前检查结果、已知限制 |

E1、E2、E3 可分别推进；E4/E5 由同一条集成线维护，避免同时修改任务状态与 PPT 接口造成冲突。每项单独保留变更和测试证据，不把五项捆绑成不可拆分的大重构。

## 4. 每项如何实施

### E0：锁定当前事实，形成可复现起点

1. 登记当前提交、已有修改文件、实际启动方式、有效配置来源。仅保存允许公开的参数和指纹，不导出密钥或私有资料正文。
2. 记录实际使用的对话模型、嵌入模型、视觉/语音后端及量化方式。区分 README 默认值、Tauri 注入值与进程实际值，不从函数名称推断 CPU/GPU。
3. 记录已用评测集和索引版本，以及 Redis、PostgreSQL、SQLite、会话归档和加密资产的职责。此处只是清单，不建设备份平台或迁移存储。
4. 对五项问题建立最小反例；源代码检查与运行复现分别标注。所有写入类测试使用临时工作区及虚构密钥，避免把用户项目当测试库。
5. 写入本次定点测试结果、既有失败和尚未检查项。已有失败不能混入新修改的成绩，也不能删除用例以制造全绿。

**通过条件：**任何后续候选都能指向一个当前问题、一个反例和一个相同条件的比较基线。E0 不需要等待新的大型业务集、购买模型服务或部署新平台。

### E1：发行启动不再携带开发解锁捷径

**入口：**Tauri 两条启动分支、`core/sidecar_runtime.py`；现有 `tests/test_sidecar_runtime.py`、`tests/test_package_sidecar.py`。

1. 开发便捷解锁保留在明确的开发分支；发行子进程不注入开发开关和开发口令。
2. 发行启动还要移除从父环境继承的同名开发变量。只是不再主动设置变量，不能防止继承值继续生效。
3. 两条子进程构造路径采用相同规则。发行包和源码启动的行为分别说明，不顺手改模型、数据库连接或工作区位置。
4. 用新建测试工作区验证：发行启动保持待初始化/待解锁；用已有测试密钥库验证正常口令仍可解锁、错误口令仍失败。
5. 对实际发行形态重复以上检查。Python 测试和 `cargo check` 不能替代这个步骤。

**验收反例：**开发变量未设置/父环境设置、两种启动路径、新/已有工作区、重启。发行路径不得自动使用开发凭据初始化或解锁测试库。

**兼容与回退：**不修改已有密钥库、不批量重加密、不自动更换用户口令。若用户工作区只有开发口令且需要迁移，应作为独立、可审阅迁移处理，不能夹在代码修复中。实际包验证失败时，交付代码候选和失败记录，不称发行问题已解决。

### E2：修正摘要偏置，并诚实呈现保留范围

**入口：**`core/conversation_compaction.py`、`core/conversation_store.py` 的 `write_summary`、`core/state_backends.py` 的压缩/持久化；必要时调整 `core/mcp_server.py` 的摘要注入。测试入口为 `tests/test_conversation_store.py`。

1. 明确区分“本次输入区间”“实际摘录的消息 ID”“是否截断”。保留旧范围字段的兼容读取，新增可选摘录字段；旧摘要的摘录范围应显示未知，不能回填猜测值。
2. 默认摘录先覆盖即将离开近期窗口的较新消息，在预算内选取后按时间顺序呈现，避免每次都被最早的长消息占满。保持字数预算，不引入额外 LLM 摘要请求。
3. 将新增信息贯通归档写入、读取和缓存，不能只改构造函数而在 `persist_summary` 中丢掉字段。对自定义摘要构造器无法确定的摘录信息，明确标记未知。
4. 注入文本注明它是有限历史摘录；项目、资料版本和所选实验继续使用当前结构化上下文，不能从摘要重新猜测这些已有字段。
5. 利用现有历史回源读取验证遗漏原文可找到。连续压缩及超过 200 条时保留各版摘要和原文，不声称单份摘要覆盖整个会话。首轮不新增自动长期记忆提取器。

**验收反例：**64 条长消息、超预算单条、空消息、超过 200 条、连续压缩、重启、Redis 不可用时回源、项目切换；新写入元数据能往返保留，原文内容与数量不变。

**明确限制：**较新优先也可能遗漏早期重要约束。本项解决选取偏置和覆盖失真，不能证明任意约束永久保留。若主流程必须依赖长期自由文本约束，应后续增加用户可确认的约束卡，再单独验收；不能把此次修复包装成长期记忆完成。

### E3：将同条件重复与条件变化比较分开

**入口：**`core/experiment_ledger.py`；`tests/test_experiment_ledger.py`、`tests/test_experiment_measurement_versioning.py`、`tests/test_mcp_server_projects.py`。

**拟采用的具体契约：**

| 字段/条件 | 重复统计 | 两次运行差异比较 |
| --- | --- | --- |
| 项目、实验 | 同项目、同实验 | 遵循已有比较范围，不扩大跨项目能力 |
| 数据集版本、评测脚本 | 非空且一致，否则阻断 | 继续遵循现有可比性门 |
| 指标定义、单位、划分、方向 | 一致，否则返回具体冲突 | 继续遵循现有完整匹配门 |
| 配置/环境引用 | 已知不同则不能标为同条件重复；缺失则无法确认 | 可以不同，但仅作为变化因素，不能直接宣称因果 |
| 随机种子 | 只有业务已声明种子可变时才作为重复因素 | 不自行从文件名或不同配置中推断 |

1. 先把上表和不兼容返回样例写成契约。它涉及重复性的解释，按 AGENTS 的统计/指标审核规则处理，不能当普通重构静默上线。
2. 保留现有 `config-a` 对 `config-b` 的差异比较用例；另建同配置/环境的重复运行用例。现有测试中将两者聚合的断言应按已确认契约调整，不能只加新测试却保留矛盾旧断言。
3. 复用现有字段进行检查。任一选中运行不符合契约时，首轮返回不适用原因及原运行列表，不自动选取一部分样本后给出“总体均值”。
4. 检查同一运行的重复指标键，防止一条运行被计作多个独立重复；输入 ID 去重后，`run_count` 和每个指标的样本数必须可核对。
5. 首轮保留当前均值、样本方差和 `normal_approximation` 方法标记，明确 n；n=1 不提供方差/区间。不顺手换成 t 区间、bootstrap 或显著性检验。
6. 引用相同只能证明登记值相同。没有内容指纹时不得称“实际配置内容已验证一致”；缺失信息返回待补齐，不自动读取解析整个配置仓库。

**验收反例：**缺失/不同数据集、脚本、配置和环境；混合项目/实验；方向或单位冲突；同运行重复指标；重复 ID；输入换序；n=1/n=2；测量修订后重新读取来源。

**退出条件：**所有选中运行为什么能/不能聚合均可说明；旧差异比较正常；统计方法与研究协议没有未经确认的变化。若重复条件尚未明确，可以先保留差异比较并显示“暂不能确认同条件重复”，不阻塞其他修复。

### E4：先显示实际 PPT 大纲，再确认生成

**入口：**`core/presentation_service.py`、`core/task_journal.py`、`core/project_catalog.py`、`core/mcp_server.py`、`core/tool_registry.py` 和现有 PPT 前端。保留 OpenXML 渲染服务及声明式风格 Skill。

**推荐最小设计：两段任务，复用现有持久化。**

`计划任务：收集选定证据 → 生成并保存实际大纲 → 完成`

`界面显示待确认计划 → 用户确认这一版本 → 生成任务：渲染 → 校验 → 返回产物`

采用两段任务，可以直接复用现有 pending/running/completed 等状态，避免为了一个确认点重建带 CHECK 约束的任务状态表。界面仍呈现一个 PPT 流程，内部两段任务以计划 ID 关联。

1. 保存实际页标题、要点、逐页证据引用、所选来源版本以及风格参数；初始记录为 draft。参数提交不再算实际大纲已确认。
2. 大纲正文和证据快照放在已有加密任务输出中；目录只保存必要引用和状态，避免新建一份未加密的完整上下文副本。
3. 返回可审阅计划。首轮只支持查看、确认、返回修改生成参数并产生新计划；不新增自由排版或完整幻灯片编辑器。计划创建携带请求 ID，同一次提交重试返回同一计划；相同请求 ID 携带不同内容应拒绝。
4. 确认请求绑定计划 ID 与内容摘要值。服务端读取已存计划生成，不接受客户端另传一份未经确认的渲染正文；摘要值用于版本绑定，不冒充认证机制。
5. 重复确认同一计划返回同一生成任务。生成任务 ID 或唯一键由计划标识稳定派生，避免两个并发确认创建两次输出；已有任务的输入绑定不一致时应拒绝。首轮采用简单重开规则：取消后或用户主动重做时，以新的请求 ID 创建新计划并重新确认；同一个重开请求重试仍返回同一新计划。失败/中断后的继续执行走已有任务的 resume，不混同于重新生成。
6. 生成任务持久化确认记录、计划和来源绑定，作为执行依据；目录显示为其投影。两套存储之间出错时可重试同步，不能要求它们天然支持跨库原子事务。
7. 生成前检查来源绑定仍可用。已存在版本的来源按版本处理；尚未绑定版本的来源至少保存稳定指纹，无法取得可信来源绑定时停在计划阶段。内容变化需新计划/新确认。
8. `/presentations/generate`、恢复入口、工具入口和前端都使用同一服务校验。接口/任务种类变化需同步客户端；不能只在前端隐藏按钮。
9. 已完成旧任务保留查看。没有实际计划确认记录的旧未完成任务，不能通过旧 resume 跳过新门，应引导重新生成/确认计划。已完成步骤产物不自动覆盖。
10. 恢复时仅复用与计划指纹、任务身份和完整性校验相符的文件。现有“页数相同就复用”不足以证明内容相同，需要额外核对关联记录。

**验收反例：**未确认不渲染；计划已完成不等于 PPT 已生成；重复/并发确认；取消后重开及重复重开请求；内容或来源变更；跨项目计划；重启后确认；绕过 UI 调工具；旧任务恢复；目录同步失败；已有同页数但不匹配的文件。

**输出：**一个真实、可打开且可编辑的 PPT，附对应大纲与证据映射。文件结构校验和实际视觉检查都要做。新输出按任务使用独立名称，不覆盖用户文件。

### E5：停止行为以步骤边界为准

**入口：**`core/task_journal.py`、PPT 服务/API/前端。首轮不承诺同一机制控制索引器、整个模型进程或其他任务类型。

1. 在现有任务表增量增加可空的取消请求时间字段，默认无请求。通过列检查执行可重复的添加迁移，不重建状态表，不用 failed 假装取消。
2. API 记录请求后，界面先显示“正在停止，等待当前步骤结束”。pending 可直接进入 cancelled；running 在步骤返回后进入 cancelled；完成任务收到晚到请求仍保持 completed。
3. 领取下一步骤前，在同一数据库事务中检查任务状态和取消请求。步骤完成/异常与最终任务完成写入也要检查状态，防止将已取消任务覆盖成 completed 或 failed。
4. 当前同步 handler 允许结束，已有输出保留并记录。取消只保证不继续领取后续步骤，无法撤销已开始的渲染或文件写出。
5. cancelled 保持不可恢复；用户重新开始时按 E4 创建新计划、重新确认后创建新生成任务。因崩溃 interrupted 的任务可按已确认计划和已完成步骤恢复。带取消请求的孤儿任务不能被启动恢复逻辑重新执行。
6. 默认恢复流程不自动打开 WPS，用户从结果入口手动打开。已经发起打开后的崩溃无法可靠判断外部窗口状态，因此不承诺该副作用严格执行一次。
7. PPT 列表同时显示当前步骤、等待确认/请求停止/实际终态和结果入口。只改现有任务区域，不新增全局调度中心。

**验收反例：**开始前、步骤执行中、文件写出后、最后一步提交附近取消；重复取消；取消与恢复并发；停止后重启；旧数据库加列；处理器异常与取消同时出现。用可控阻塞 handler 和临时文件检查调用次数，避免靠人工点击时机碰运气。

**回退边界：**测试旧库可读取，重复初始化不报错；部署前只允许在测试库验证迁移。回退程序前停止任务执行，并核对旧程序对新字段/任务种类的处理；不能用旧程序继续执行含取消请求的新任务。用户库变更前另行形成备份及恢复步骤，不把“加列简单”当作可以省略验证。

### E6：对三条 PNG 失败做有终点的诊断

**输入：**现有 B1 结果中的 `CP-RAG017`、`CP-RAG018`、`CP-RAG028`，保持原数据及预期来源不变。

1. 分别检查原文件是否存在、是否成功摄取、是否有 OCR/描述文本、是否保留正确项目/来源信息。
2. 查看该问题的关键词和向量候选、重排结果及最终证据，定位失败发生在摄取、过滤、召回、重排、视觉路由还是回答阶段。
3. 先判断是否因现有能力没有被正确使用。只有定位后才提出一个最小候选，不能直接默认换 VLM、加图数据库或加查询 Agent。
4. 为对应回放记录实际提供方、模型、输入范围与各阶段耗时。现有产品结果有 `elapsed_ms`，但检索/生成分项为空；空值保留为未测，不能填零。
5. 可复现的现有回归问题进入独立修复；若需要新标注、扩展截图范围或新增模型资源，则提交具体方案，E6 到诊断报告即结束。

**通过条件：**三项各有“在哪一层失败、证据是什么、下一步需要什么”的记录。不要求人为把三项都改为通过，更不能只修改预期答案。

**性能边界：**8 GB 显存下先记录模型装卸、串行/并行实际行为与峰值；不默认让视觉、嵌入和对话模型同时驻留。小样本时间用于诊断，不能包装成稳定 P95 或固定响应承诺。

### E7：验收本机单项目流程

1. 先用已有项目包走通流程；需要真实用户资料时仅使用已授权、版本清晰的项目。数据与口径变化按现有规则审阅，不能边调参边改验收数据。
2. 在该项目内选择文本报告、CSV/XLSX 指标和对应配置，核对摄取结果与来源。语音/截图可作为独立附加入口，不改变文本主线的验收终点。
3. 发起一次时间范围明确的比较；有缺失或多个等价候选时要求选择；可比时核对数值与来源，不可比时检查原因提示。
4. 用上述证据生成实际 PPT 大纲，查看来源，确认生成，再离开和返回任务；打开 PPT 检查中文、布局、引用和可编辑性。
5. 在独立任务上执行一次步骤间停止和一次崩溃恢复，检查状态、调用次数、文件与计划身份。不要通过杀死用户真实推理服务做破坏性演示。
6. 运行范围相关回归，再运行仓库已有 `scripts/check.ps1`；按当前环境记录失败原因。额外完成真实 Tauri/发行形态检查，不能只凭 UI build 或源代码正则测试交付。
7. 记录运行条件、步骤结果、产物和日志位置、未解决项。演示成功只证明该流程；全项目质量和竞赛/隐藏测试结论另列。

**用户可验收的结果：**能找到正确项目证据；不能比较时有明确原因；确认的是实际大纲；任务能找回、停止和按边界恢复；PPT 可打开；发行行为符合说明。

## 6. 首轮之后，哪些模块值得做

以下是有业务依据的候选，不进入 E0–E7 的承诺范围；每次只选择一个满足准入条件的模块。

| 优先顺序 | 候选模块 | 启动证据 | 最小下一步 | 何时不做 |
| --- | --- | --- | --- | --- |
| 1 | 文件摄取诊断与手动更新预览 | 用户多次遇到无法入库、旧版本或来源不清 | 在现有资料列表显示失败阶段/原因，手动预览新增与变更；沿现有索引接口更新 | 没有可复现摄取/更新问题时不建全量目录同步 |
| 2 | 工作区备份与隔离恢复 | 存储边界已登记，需要承担长期资料保存 | 先明确停写顺序、保存范围与密钥依赖，编写人工操作规程并在测试工作区恢复一个项目 | 未通过恢复演练前不加“一键恢复”宣传或在线协调快照 |
| 3 | 来源变化提示 | 已发生“源数据改了，报告仍用旧版本” | 利用现有来源版本，仅提示该 PPT 需要重新核对 | 未证明版本关联准确前不自动传播/局部重生成 |
| 4 | 项目约束卡 | 长对话反复遗漏用户明确要求，且用户愿意确认结构化信息 | 先做可查看、编辑、撤销的少量项目约束，并与事实证据分开 | 不从所有聊天中自动提取并永久写入记忆 |
| 5 | 报告导出 | 用户经常将同一证据手工整理成报告 | 复用已确认大纲生成带引用的 Markdown 文件；确有可编辑 Word 需求再做 DOCX | 不能因为支持 DOCX 输入就声称有成熟报告导出 |
| 6 | 固定业务模板与单个连接器 | 同一手动任务已稳定重复，且有明确外部来源 | 先固化一个手动流程，必要时连接一个已选工具；独立评测 | 没有真实消费者时不建通用 MCP 客户端、插件市场或 Agent 群 |
| 7 | 本地例行任务 | 手动模板、幂等、恢复和通知行为全部通过 | 再加入本地定时触发及休眠后处理 | 不承诺电脑休眠/程序未运行时准时执行，不默认发送邮件/写日历 |

UI 整理跟随具体业务发生：在已修改区域提取组件、补错误提示和结果入口；不以 `App.tsx` 或服务文件较大为理由整体重写。当前声明式 Skill、现有混合检索和本地模型资源切换继续复用；本计划不将 REST 工具目录表述为已经实现标准 MCP 协议。

## 7. 外部项目如何转化为本地操作

外部资料只证明某种做法有可参考实现，不能证明 SoulDrive 直接采用就有效。以下取舍来自官方资料与当前代码的对照，不代表引入这些系统作为依赖。

| 参考 | 可核查做法 | SoulDrive 的有限采用 |
| --- | --- | --- |
| [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) | 持久化状态后等待外部输入；恢复时部分代码会重新执行 | E4 保存实际计划再确认，E5 测试恢复副作用；用现有任务日志实现 |
| [Claude Code Checkpointing](https://code.claude.com/docs/en/checkpointing) | 会话/编辑回退有明确边界，不能覆盖所有外部副作用 | 说明任务恢复、文件结果和外部窗口的不同状态；不承诺任意操作回滚 |
| [Open WebUI Knowledge](https://docs.openwebui.com/features/workspace/knowledge/) | 资料管理、异步摄取及基于文件信息的同步机制 | 后续先做摄取失败提示和手动更新预览，避免直接引入自动删除同步 |
| [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/) | 运行关联参数、指标与产物 | E3 利用现有运行元数据判断重复/比较，不部署第二套实验平台 |

前两版已检索 Codex、AnythingLLM、Docling、RAGFlow 等资料，候选背景保留在 V2。最终执行范围不按项目名气排序；直接对应当前缺口的机制才保留。对标 Codex/Claude Code 的方向落实为上述任务透明、上下文可核对和受控交付，不将其产品体量或模型能力列为本项目短期承诺。

## 8. 最终交付判定

本计划可以作为下一轮实施依据：首轮主线、代码入口、依赖、反例、操作顺序和不能承诺的部分均已明确。**V2 中“首版同时完成全面资料更新、长报告、依赖传播和备份平台”的安排不再采用。**

实施后的“完成”须同时满足：范围内反例和旧回归通过，实际 UI/产物通过，相关发行形态行为已验证，未解决边界在交付说明中可见。统计语义、冻结数据、用户库迁移等仍按仓库明确的审核门执行，不能由计划措辞自动授权。

现阶段准确的承诺是：先交付一个可审阅、可停止、能追溯结果的本机项目流程，再由实际使用问题决定新增模块。代码与本次 59 项测试提供了实施基础；性能收益、泛化、多模态增益和完整产品成熟度仍需后续实际验证。
