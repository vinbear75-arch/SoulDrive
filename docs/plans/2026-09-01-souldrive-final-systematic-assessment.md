# SoulDrive 项目收尾阶段系统评估报告

> 评估日期：2026-09-01  
> 适用版本：当前 `main` 工作区及其未提交改动  
> 评估目标：在尽快收尾的前提下，保留并强化比赛含金量，停止低收益扩张  
> 结论等级：代码事实、当前本机回归、已保存评测结果和公开资料联合审计

## 1. 执行结论

SoulDrive 当前的主要问题已经不是“功能太少”，而是以下四项没有形成闭环：

1. **实现很多，但尚未冻结成可复现提交版本。** 当前工作区有 563 个变化路径，其中 83 个为已跟踪修改、480 个为未跟踪条目；大量比赛核心代码和评测证据不在当前 Git HEAD 中。
2. **多模态功能已经能运行，但比赛级价值证据仍不足。** 真实授权集只有 10 条，且集中在一个演示项目，缺少跨说话人、分辨率、应用、项目冲突和图标/图表覆盖。
3. **最大技术阻塞是完整链路延迟，不再只是 VLM 冷启动。** 当前真实 10 条完整快路径的完整回答 P95 约 35.1 秒；启用 VLM 后约 81.4 秒，均无法支撑“小于 5 秒”的正式声明。
4. **项目含金量没有充分呈现在一条可量化故事中。** 项目空间、RAG、实验账本、证据门、多模态、个性化、PPT、邮件、日程、Skill 都已存在，但如果并列展示，会显得像功能集合，而不是一个围绕科研实验诊断的创新系统。

因此，本报告的最终建议是：

- **今天不再增加横向功能。** 先修复评测语义、冻结代码和证据、完成文档与演示提交。
- **如果作品已提交并为决赛迭代，只增加三项：**“5 秒硬预算证据快答”“多模态消融回放”“实验差异证据卡”。
- **其他功能全部冻结。** 特别是邮件服务商、真实日历写入、更多 PPT 风格、通用桌面自动化、云协同、更多模型和新的 RAG 框架。

一句话说：

> SoulDrive 不需要再变大，需要把“指着实验结果问为什么比上个月差”这一条链路做快、做真、做成可重复实验。

## 5. 当前最有含金量的三项能力

### 5.1 项目、时间、版本约束下的实验诊断

这不是普通 RAG。SoulDrive 已经具备：

- `project_id` 约束；
- 实验、run、metric、measurement 结构；
- “上个月”的时间区间解析；
- 数据集版本、评测脚本、指标名称、单位、split、方向可比性门控；
- 变化值绑定源文件、sheet、row 或 line；
- 不可比时阻断数值差异计算。

这部分最接近真实科研生产力，也最容易被评委理解。它应成为主产品价值，而不是被“本地知识库”“发邮件”“做 PPT”等功能冲淡。

关键本地证据：

- `core/experiment_ledger.py`
- `core/project_catalog.py`
- `eval/results/experiment_comparability_gate_recheck_20260830.json`
- `eval/results/rag_experiment_measurement_bridge_recheck_20260830.json`

### 5.2 类型化证据与保守生成

SoulDrive 已把证据区分为：

- `E#`：文档证据；
- `V#`：视觉证据；
- `A#`：确认后的语音证据；
- `M#`：结构化实验测量。

当前实现还对引用内容是否支持 claim 做本地词法校验，并对数字事实进行额外约束。这比“给回答附几个引用链接”更有技术价值，因为它在系统层限制不同来源的证据权限。

关键本地证据：

- `core/answer_quality.py`
- `core/rag_engine.py`
- `eval/results/rag_claim_support_recheck_20260830.json`
- `eval/results/rag_answer_quality_eval_recheck_20260830.json`

### 5.3 可靠性感知的多模态目标绑定

系统没有简单拼接语音与图像，而是使用 UIA、OCR、授权选区、VLM 候选、时间原点、空间范围、项目 ID 和置信度共同决策，并在歧义时澄清。

这条路径在当前 10 条真实授权 pilot 上把目标绑定从 text-only 的 0 提升到 1.0。这个结果只能说明当前 pilot 的目标绑定收益，不能外推成完整业务准确率，但它足以成为创新主线的原型证据。

关键本地证据：

- `core/soulalign.py`
- `core/topic5_runtime.py`
- `core/interaction_context.py`
- `eval/results/real_mmi_full_chain_fast_intent_fix_20260830/metrics.json`

## 6. 当前最严重的五个问题

### 6.1 P0：工作区未冻结，提交不可复现

当前 Git HEAD 仍为 `0e216835775a93ed263e57911b6d6aa31d813acc`，但本轮审计看到 563 个变化路径。很多核心模块、测试、配置、演示数据和评测结果仍是未跟踪内容。

风险包括：

- 打包或换机时漏掉比赛核心代码；
- 文档中的哈希与实际提交包不一致；
- 评测结果无法回到唯一代码版本；
- 后续修复覆盖当前可运行状态；
- 演示机和提交源码不是同一版本。

这比新增任何功能都更紧急。

### 6.2：个性化泄露率指标已修复

`cross_project_leakage_rate` 已改为“实际泄露样本数 / 总样本数”，并补充了 0、0.5 和 1.0 三种最小契约测试。最新结果文件为 `eval/results/personalization_pair_seed_final_20260901.json`：2/2 通过，事实与引用不变，交叉项目泄露率为 0.0。

该结果仍只是 2 对冻结种子样例的契约验证，不代表真实用户规模下的个性化收益；后续扩样本前不扩大结论。

### 6.3 P0：完整链路延迟远高于目标

当前保存结果显示：

| 路径 | 总延迟 P95 | 首 token P95 | 完整回答 P95 | 关键说明 |
| --- | ---: | ---: | ---: | --- |
| 真实 10 条，视觉快路径 | 35.24 s | 25.25 s | 35.11 s | VLM 全部跳过，仍未满足 5 秒 |
| 真实 10 条，VLM 慢路径 | 93.22 s | 27.32 s | 81.35 s | VLM 阶段 P95 约 19.57 s |

因此，问题已经不能被描述成“只要预热 VLM 就能解决”。8GB 显存下，ASR、OCR、重排、3B 聊天模型和约 7GB VLM 权重之间的模型驻留/切换，使完整链路成本很高。

### 6.4 P0：真实多模态数据不足

当前真实集审计结果：

- episode：10；
- 项目：仅 `demo_project`；
- split：全部为 `seed`；
- 说话人、分辨率、应用和目标类型统计为空；
- 文字、图标、图表、时间错位、项目冲突、低置信度、OOS 覆盖均未满足；
- 审计状态：`valid=false`。

合成 480 条可以验证评测器和链路，不可替代真实业务结论。

### 6.5 P0：提交材料仍是提纲，不是最终作品

当前 `docs/competition_submission_draft.tex` 仍包含：

- `[团队名称]`；
- `[成员1]`、`[成员2]`、`[成员3]`；

现有 PPT 大纲也主要是文字条目，缺少正式架构图、主实验表、消融表、延迟分解和失败案例截图。

## 10. 提交后最值得增加的三项功能

### 10.1 P1-A：5 秒硬预算证据快答

#### 为什么值得做

当前最大的比赛阻塞是完整回答延迟。继续优化一个 80 秒级慢链路，风险高；最小可行方式是把主任务拆成“确定性证据快答”和“可选深度分析”。

#### 最小产品形态

用户框选实验指标并提问后，系统在一次完整响应中直接返回：

1. 当前绑定的目标、项目和时间；
2. 基线值、当前值、绝对/相对变化；
3. 可比性门是否通过；
4. 直接来源 `M#/E#/V#/A#`；
5. 若不可比，返回缺失字段和澄清问题；
6. 若可比，返回“已证实变化”，不在 5 秒路径上生成未经证明的原因。

该响应使用现有结构化实验账本和抽取式证据，不强制调用聊天模型或 VLM。深度原因分析作为明确的第二次用户操作，不把异步补全冒充本轮小于 5 秒。

#### 实现边界

- 不新增模型；
- 不新增数据库；
- 不重写 RAG；
- 复用 `experiment_ledger`、`EvidencePanel`、SoulAlign 决策和现有事件账本；
- 增加统一的 `deadline_ms` 和逐阶段剩余预算；
- 超预算时返回完整、保守、可引用的确定性结果。

#### 验收

- 当前 10 条 pilot 先达到全响应 P95 小于 5 秒；
- 决赛前在至少 30 条真实冻结 episode 上复测；
- wrong-project rate 为 0；
- 不可比样本 100% 阻断数值变化；
- 所有数值有 `M#` 或可定位 `E#`；
- 深度路径单独报告延迟，不与快答混算。

### 10.2 P1-B：多模态消融回放

#### 为什么值得做

多模态的真正含金量不是“能上传语音和图片”，而是证明时间、空间、项目和冲突门控分别解决了什么问题。当前系统已有事件账本和录制素材，缺少的是可重复的同条件对照。

#### 最小产品形态

对同一个冻结 episode 一键回放四个版本：

- text-only；
- 完整模态；
- 去时间对齐；
- 去项目元数据；
- 可再加入“去冲突澄清”作为第五项。

输出一张配对表：

- intent 是否正确；
- target 是否正确；
- 是否检测冲突；
- 是否应澄清；
- 是否串项目；
- 每阶段延迟；
- 证据引用是否有效。

#### 实现边界

- 先做离线脚本和 JSON 报告；
- UI 只展示汇总表，不制作复杂实验平台；
- 不生成新数据，不修改 sealed-test；
- 每次只比较一个去除因素。

#### 验收

- 同一个 `episode_id` 的所有变体共享相同输入资产和 gold 标签；
- 结果保存逐样本而非只保存平均数；
- 能明确指出至少一类 full multimodal 相对 text-only 的稳定收益；
- 如果没有稳定收益，材料中停止宣传该模态。

这正是 OpenAI Docs 所强调的 scored improvement loop：先定义可机读评测和停止条件，每次只做一个改动，再记录分数与产物，而不是靠不断增加功能获得“看起来更强”的效果。

### 10.3 P1-C：实验差异证据卡

#### 为什么值得做

后端已经有严格比较、证据版本和原因边界，但这些价值没有在 UI 中形成一眼可见的比赛亮点。

#### 最小产品形态

把现有实验比较结果汇总成一张卡：

- 当前 run 与基线 run；
- 数据集、split、脚本、单位、定义是否一致；
- 指标变化；
- 对应源文件与定位；
- 已证实原因/高可信候选/待验证假设/无法确定；
- 最小区分实验；
- “生成组会稿/PPT 草稿”按钮。

#### 实现边界

- 不引入新图数据库；
- 不增加通用因果模型；
- 不让 LLM 把相关变化写成已证实原因；
- 只展示已有 `experiment_comparison` 和 `M#` 证据。

#### 验收

- 不可比时卡片不显示百分比变化；
- 任一数字可以回到 source locator；
- 原因等级和证据类型在 UI 上可见；
- 演示者不需要打开日志解释系统做了什么。

## 11. 可选的比赛演示模式

如果前三项完成且仍有时间，可增加一个极薄的“比赛模式”，不改变后端：

- 默认进入唯一演示项目；
- 隐藏邮件发送、日程、Skill 管理、通用诊断等旁支入口；
- 固定显示“感知 → 对齐 → 比较 → 证据 → 草稿”五阶段；
- 显示每阶段耗时和降级原因；
- 保留失败样本切换。

这不是技术创新，而是减少评委认知负担。只允许通过一个 UI 状态或配置实现，不为比赛另建前端。

## 12. 值得优化但不应立刻重构的现有模块

### 12.1 RAG

值得优化：

- 修复 `CP-RAG-017` 的图像标题/视觉资产检索缺口；
- 统一离线 0.5 秒检索与完整链路 24 秒检索的运行口径；
- 将答案质量、引用合法、claim 支持和检索命中分开报告；
- 对当前 30 条生成结果运行正式答案评测，而不是只统计非空回答。

不值得做：

- 再加入一个向量数据库；
- 再调一轮没有冻结基线的融合权重；
- 为 GraphRAG 增加更多实体关系；
- 引入完整 PaperQA2 服务栈。

### 12.2 多模态

值得优化：

- 明确模型驻留与显存交接策略；
- 将 UIA/OCR/显式框选设为主路径；
- 只在无法通过结构化路径回答时调用 VLM；
- 用统一 deadline 控制模型加载、推理和回答生成；
- 保存路由原因和阶段预算。

不值得做：

- 把每张截图都送给 VLM；
- 为图标能力立刻增加常驻大模型；
- 做后台全屏持续录制；
- 做通用点击/键盘控制 Agent。

### 12.3 个性化

值得优化：

- 先修指标语义；
- 把种子对从 2 对扩到至少 12 对人工复核样本；
- 验证删除/撤销后的残留率；
- 验证不同项目画像不交叉。

不值得做：

- 自动推断大量隐式偏好；
- 让偏好改变事实或数值；
- 新增画像推荐模型。

### 12.4 工程结构

`souldrive-ui/src/App.tsx` 约 6,592 行，`core/mcp_server.py` 约 5,121 行，`core/knowledge_base.py` 和 `core/rag_engine.py` 也已经很大。长期应拆分，但提交前重构风险远大于收益。

当前只做：

- 封版检查入口统一；
- 关键错误修复；
- 竞争主路径的最小增量；
- 不进行“大文件治理”式重构。

## 13. 开源项目与 Codex/Claude Code 的最终借鉴结论

### 13.1 OpenAI Codex：借鉴评测闭环，不借鉴更多工具数量

OpenAI Docs 对复杂任务的建议是建立 scored improvement loop：机器可读评测、明确阈值、逐次单因素改动、运行日志和对产物本身的检查。SoulDrive 已有大量零散评测，下一步应统一成一个“当前基线 → 最大失败 → 单一修改 → 重跑 → 停止”的封版流程。

参考：

- [Iterate on difficult problems](https://learn.chatgpt.com/use-cases/iterate-on-difficult-problems)
- [Add evals to your AI application](https://learn.chatgpt.com/use-cases/ai-app-evals)

不建议现在引入 Promptfoo；现有 Python 评测已经足够，关键是统一入口与停止规则。

### 13.2 Claude Code：权限强制应位于模型之外

Claude Code 官方文档将权限分为 deny、ask、allow，并明确权限由宿主执行而不是由模型提示词保证。SoulDrive 当前邮件、日历、删除、Playbook 和授权屏幕边界已经采用相同原则。

参考：[Claude Code permissions](https://code.claude.com/docs/en/permissions)

结论：这部分不需要再增加功能，只需要在答辩中把现有确认门展示清楚。

### 13.3 OmniParser：只做冻结基线上的图标检测候选实验

OmniParser 在 2026 年 7 月加入 YOLOv9-E interactive region detector，官方仓库说明新 detector 基于 MIT 许可实现；较早 Ultralytics 检测器仍有 AGPL 继承风险。

参考：[Microsoft OmniParser](https://github.com/microsoft/omniparser)

SoulDrive 当前图标准确率只有 1.9%，因此该候选有潜在价值，但不能今天直接接入。正确流程：

1. 单独环境下载权重；
2. 在当前 1,272 条 ScreenSpot 保存集上同条件重跑；
3. 检查许可证、模型体积、P95 和显存；
4. 只有图标准确率显著提升且端侧预算可接受时再集成；
5. 未超过基线则删除候选，不增加生产依赖。

### 13.4 PaperQA2：现有机制已足够，不引入完整依赖

PaperQA2 的重要机制是 query-dependent contextual summary、重排、带引用回答和可复现实验。SoulDrive 已经实现了候选摘要、支持度、重排和引用门。

参考：[Future-House PaperQA2](https://github.com/future-house/paper-qa)

当前项目使用 Python 3.10，而最新 PaperQA2 要求 Python 3.11+，且默认工作流更偏云端和外部元数据。为了收尾，不应引入该依赖。

### 13.5 MLflow：继续支持本地导出，不部署服务

MLflow 官方将 run 视为包含指标、参数、时间和产物的执行记录，并强调模型、指标和数据集之间的可追溯链接。SoulDrive 已支持本地 MLflow run 目录/归档解析和严格比较。

参考：[MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/)

当前不需要启动 MLflow Server；继续摄取本地导出即可，避免增加部署复杂度。

## 14. 真实评测的最小方案

### 14.1 数据目标

决赛前至少完成 30 条真实授权 episode，不要立即追求 480 条真人数据。

建议分配：

| 类型 | 数量 |
| --- | ---: |
| 文字/UIA/OCR 明确目标 | 8 |
| 图表或复杂布局 | 5 |
| 语音指代与时间错位 | 5 |
| 项目冲突与跨项目干扰 | 4 |
| 低置信度与应澄清 | 4 |
| OOS/越权/不可逆动作 | 4 |

至少覆盖：

- 2 个说话人；
- 2 种分辨率；
- 3 个项目；
- 2 个应用窗口；
- 多种“这个/刚才/上个月”指代；
- 明确可比和明确不可比实验。

### 14.2 必须保存

- 原始授权音频/截图或 UIA 快照；
- ASR/OCR/VLM 输出与置信度；
- SoulAlign 决策；
- 项目、时间和选区；
- text-only/full/no-time/no-project 逐样本结果；
- 检索证据；
- 首次有效响应和完整响应延迟；
- gold 标签与人工复核；
- 失败原因。

### 14.3 主要指标

- Intent Accuracy；
- Target Binding Accuracy；
- Conflict Detection Accuracy；
- Clarification Precision/Recall/F1；
- Wrong-project Rate；
- Citation Validity；
- Claim Support Precision/Recall；
- 全响应 P50/P95；
- 峰值显存；
- 降级率和失败率。

## 17. 答辩中的主故事

只演示一个故事：

1. 用户在当前项目中框选一个下降指标；
2. 用户说：“这个为什么比上个月差？”；
3. 系统显示语音、选区、项目和时间对齐；
4. 如果存在多个历史候选，系统先澄清；
5. 系统检查数据集、split、脚本、单位和指标定义是否可比；
6. 5 秒内返回确定性差异证据卡；
7. 用户选择“深度分析”后，系统展示文档、日志和结构化测量；
8. 结果区分已证实原因、高可信候选和待验证假设；
9. 系统生成最小验证实验；
10. 用户确认后生成带引用的组会/PPT 草稿；
11. 系统展示未发送、可撤销和审计记录。

评委应在三分钟内看到：

- 多模态为何必要；
- 项目/时间/版本为何必要；
- 证据如何限制模型；
- 系统如何处理失败；
- 真实指标和边界是什么。

## 20. 最终建议

SoulDrive 已经有足够多的功能，甚至已经存在功能过宽的风险。接下来不要用“再加一个模型、一个 Agent、一个连接器”提升含金量；真正的含金量来自：

1. **同一个真实问题能否在项目、时间和版本约束下正确理解；**
2. **多模态是否通过消融证明有用；**
3. **答案是否被可定位证据和可比性门约束；**
4. **端侧完整响应是否达到明确延迟门槛；**
5. **代码、数据、指标和演示是否可复现。**

收尾阶段的正确产品路线是：

```text
立即封版与提交
  -> 修复指标语义和统一回归
  -> 5 秒证据快答
  -> 多模态消融回放
  -> 实验差异证据卡
  -> 30 条真实 episode
  -> 决赛材料冻结
```

做到这里，SoulDrive 的价值不再是“一个功能很多的本地助手”，而是：

> 一个能够理解用户正在指向什么、严格判断实验是否可比、用类型化证据解释变化，并在端侧安全降级的科研实验诊断系统。
