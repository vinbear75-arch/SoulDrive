# SoulDrive PC 多模态项目知识工作台：实施规格

状态：业务边界与 Harness 基线制度已确认；赛题方回复、数据许可证和最终模型计数口径待确认。

本文是后续大范围重构的主规格。产品概要见 `docs/contest_topic5_product_blueprint.md`。只有涉及赛题五、PC 多模态、项目空间、数据训练或比赛交付时才需要加载本文。

## 1. 产品的不可变主线

SoulDrive PC 面向研究生、研发人员和企业知识员工。用户围绕一个课题或项目主动导入资料，系统通过语音、当前屏幕/选区、项目上下文和个人偏好理解任务，生成带证据的回答、报告、PPT、邮件或日程草案。

核心业务闭环：

```text
项目材料 -> 结构化项目记忆 -> 多模态任务理解 -> 证据检索与分析
         -> 可解释预览 -> 用户确认 -> 版本化交付物
```

比赛首版只承诺单用户 PC、本地项目空间和确认式执行。它不承诺任意桌面自动化、不允许未经确认发送邮件、不后台全屏录制，也不把“模型给出的猜测”表述为实验因果结论。

## 2. 为什么能够真正实现

旧系统已有文档解析、父子切片、关键词/向量检索、知识图谱、OCR、交互上下文、审计、任务日志和本地 PPTX 生成能力。重构重点不是重写这些能力，而是在它们之上增加：

1. 项目和资产版本边界；
2. 实验、指标、决策和任务的结构化目录；
3. 带时间戳的语音/屏幕/UI 事件；
4. 多模态对齐、意图、目标和冲突决策；
5. 新的工作台 UI 和可复现评测。

检索不能仅依赖向量相似度。类似“上个月实验”的问题先通过项目、资产类型和时间做结构化过滤，再在候选范围中做语义检索和证据重排。

## 3. 项目空间的数据模型

### 3.1 存储分层

每个项目使用三层存储：

- 原始资产层：用户导入的源文件和版本化生成产物；
- 结构化目录层：项目、资产、实验、指标、决策、任务、模板和事件；
- 派生索引层：文本切片、关键词索引、向量索引、OCR 区域和知识图谱。

新增 `project_catalog.sqlite` 作为业务目录。现有父文档、关键词、向量和图谱存储继续作为派生索引使用；它们必须增加或继承 `project_id`、`asset_id`、`asset_version_id` 和时间元数据。派生索引可以重建，原始资产和业务目录不可依赖索引反推。

### 3.2 主要实体

| 实体 | 必填字段 | 作用 |
|---|---|---|
| `projects` | `project_id`, `name`, `status`, `created_at` | 隔离每个课题或研发项目 |
| `assets` | `asset_id`, `project_id`, `asset_type`, `title`, `source_kind` | 表示论文、方案、记录、模板或产物 |
| `asset_versions` | `version_id`, `asset_id`, `content_hash`, `file_ref`, `valid_from` | 版本追踪和可重复引用 |
| `experiments` | `experiment_id`, `project_id`, `name`, `objective` | 表示同一实验主题 |
| `experiment_runs` | `run_id`, `experiment_id`, `performed_at`, `dataset_version`, `config_ref`, `environment_ref` | 表示一次具体运行 |
| `metric_definitions` | `metric_id`, `name`, `unit`, `direction`, `definition_version` | 避免把同名异义指标混在一起 |
| `measurements` | `run_id`, `metric_id`, `value`, `split`, `sample_count`, `variance` | 保存可计算的实验结果 |
| `decisions` | `decision_id`, `project_id`, `decided_at`, `statement`, `evidence_refs` | 保存会议或评审决定 |
| `tasks` | `task_id`, `project_id`, `due_at`, `status`, `evidence_refs` | 支持待办和日程草案 |
| `profiles/templates` | 用户偏好、模板、术语和别名 | 约束个性化输出 |
| `contacts` | `contact_id`, `display_name`, `aliases`, `email`, `project_ids` | 本地收件人解析，不承担员工管理 |
| `interaction_events` | 模态、起止时间、目标、置信度、隐私级别 | 支持时序对齐和回放 |
| `artifacts` | 产物类型、来源版本、生成计划、确认状态 | 追踪报告、PPTX、邮件和日程草案 |

联系人和日历摘要保存在结构化表中，不切成普通知识块。联系人只来自用户手动添加、CSV/vCard 导入或用户确认后的选区提取，不包含部门、考勤、绩效和组织权限，也不跨设备同步。语音和截图默认是短期事件，只有用户明确保存时才成为资产。

### 3.3 时间字段的语义

系统必须区分：

- `performed_at`：实验实际发生时间；
- `authored_at`：材料撰写时间；
- `valid_from/valid_to`：版本有效期；
- `imported_at`：文件进入 SoulDrive 的时间；
- `observed_at`：屏幕或语音事件发生时间。

“上个月实验”以用户当前时区和 `performed_at` 解析，不能使用导入时间。若只能从文件名、文件修改时间或正文推断，记录推断来源和置信度；低置信度时要求用户确认。

## 4. 导入、识别和补全

### 4.1 导入流程

1. 用户先选择项目，再导入文件或保存当前选区。
2. 解析器识别标题、作者、文档类型、日期、版本、项目实体和表格。
3. 对实验型材料提取候选实验名称、运行时间、配置、数据集和指标。
4. 系统展示“导入确认卡”，用户只修正低置信度字段。
5. 写入原始资产、结构化目录和派生索引，并记录解析器/模型版本。

不能让大模型静默决定关键日期、指标单位和数据集版本。人工修正作为结构化事实保存，而不是只改一段生成文本。

### 4.2 实验材料的最低可比较字段

一次实验若要参与数值比较，至少需要：

- 实验主题和运行日期；
- 数据集名称、版本和划分；
- 模型/代码版本或配置摘要；
- 指标名称、方向、单位和数值；
- 运行环境；
- 证据所在文件、页码/表格/段落。

缺失字段时仍可被全文检索，但只能生成“文字层面的资料总结”，不能计算严格性能差异。

## 5. “和上个月实验对比”的完整执行规则

### 5.1 目标解析

1. 从当前选区和语音解析当前实验或指标对象。
2. 将“上个月”转为本地时区的闭开时间区间。
3. 在当前 `project_id` 下过滤 `experiment_runs.performed_at`。
4. 使用实验名、实体别名、数据集和指标做候选排序。
5. 没有候选时报告缺少什么；存在多个同分候选时让用户选择，不能默认取第一条。

### 5.2 可比性门控

只有同时满足以下条件才计算变化：

- 指标定义版本一致；
- 单位一致或可无损转换；
- 数据集版本和测试划分一致；
- 评测脚本版本兼容；
- 高低优劣方向已知。

模型、硬件和随机种子不同不会阻止比较，但必须显示为变化因素。若存在多次重复实验，优先比较均值、方差和置信区间；只有单次结果时明确标注“不足以证明稳定退化”。

### 5.3 原因分析边界

“找出性能下降原因”分为三级：

- 已证实原因：实验记录或消融直接验证了某个变化；
- 高可信候选：唯一显著变化与已知机制一致，但尚无对照实验；
- 待验证假设：从日志、配置或会议记录推导，必须给出建议实验。

系统先对比配置、数据、代码版本、硬件、超参数和错误日志，再检索相关会议决策。回答必须引用证据，并区分相关性与因果性。没有证据时只能说“无法确定”，同时生成最小验证实验计划。

## 6. 多模态能力的精进方向

### 6.1 首版模态

- 语音：按住说话，获得文本、词级/片段级时间和 ASR 置信度；
- 屏幕/UI：当前应用、窗口、焦点控件、系统可读选区；
- 视觉兜底：用户框选区域后的截图、OCR 文本、坐标和置信度；
- 交互：热键、鼠标选区和确认/取消操作；
- 历史上下文：当前项目、近几轮任务和显式用户偏好。

生产环境允许任意选区。评测集使用固定截图和固定选区，只为保证金标可复现。系统不通过训练记住所有界面，而是依赖用户明确触发、UI Automation 和 OCR 降级。

### 6.2 时序上下文图

把事件表示为带时间窗口和置信度的图节点；边表示“同时发生”“指向”“属于当前窗口”“来自同一项目”和“与用户偏好冲突”。候选目标的分数由时间距离、空间包含、语义相似、窗口焦点和来源可靠性共同决定。

UI Automation 选区的可靠性高于 OCR，显式鼠标选中高于仅有光标位置，当前窗口高于后台窗口。低于阈值时主动澄清。

### 6.3 快慢视觉路由

- 快路径：存在系统可读选区或高置信 OCR 文本时，只传递结构化文本、坐标和窗口信息，不运行整屏视觉推理。
- 慢路径：目标是图标、图表、布局区域，或文字目标存在多个候选时，裁剪当前授权屏幕区域并调用主视觉语言模型。
- 拒绝路径：目标超出授权区域、视觉置信度不足或涉及不可逆动作时，不扩大截图范围，直接请求用户框选或确认。

这样既保留真实视觉理解，又避免每轮处理整屏导致延迟和隐私成本。路由本身要记录触发原因、输入范围、模型耗时和最终置信度。

### 6.4 冲突类型

- 语音实体与屏幕目标不一致；
- 当前项目与屏幕文档所属项目不一致；
- 用户说“发送”但权限策略只允许生成草案；
- 语音要求覆盖文件但当前产物尚未确认；
- ASR、OCR 或时间对齐置信度不足；
- 用户偏好与本轮明确要求冲突时，本轮要求优先。

### 6.5 可选第三模态

只有赛题方确认人体视觉是内部集关键模态时，才增加摄像头手势/头部动作。它只用于确认、拒绝和指向等有限标签，不承担情绪读心，也不改变项目知识业务。原始视频仅保存在内存短时缓冲。

## 7. 公开数据集适配结论

### 7.1 已核验事实

- [MIntRec](https://arxiv.org/abs/2209.04355) 有 2,224 个来自电视剧《Superstore》的文本、音频和视频样本，标注 20 类意图。它规模较小且不是 PC 业务，只能作为旧基线。
- [MIntRec2.0](https://arxiv.org/abs/2403.10943) 有 1,245 个多方对话、15,040 个样本、30 个细粒度意图；其中 9,304 个域内样本和 5,736 个域外样本，并包含多轮上下文。它比 MIntRec 更适合作为主公开“多模态意图 + 上下文 + OOS”候选。
- [SeeClick/ScreenSpot](https://arxiv.org/abs/2401.10935) 的 ScreenSpot 覆盖移动端、桌面端和 Web GUI，任务是从截图与指令定位屏幕元素。它与 SoulDrive 的屏幕目标绑定高度相关，但没有语音、时序和项目知识，因此只能作为屏幕 grounding 辅助基准。
- [M3ED](https://arxiv.org/abs/2205.10237) 是中文多模态情绪对话集，包含 990 段双人对话、9,082 个轮次和 24,449 个话语，使用音频、视觉、文本及 7 类情绪标签。它可测试中文音视频和对话上下文，但情绪不是 SoulDrive 主任务。

另有[模态偏置研究](https://arxiv.org/abs/2508.16122)指出 MIntRec 系列可能存在较强文本偏置，因此不能只报告全模态总分；必须增加遮蔽文本、缺失音频/视觉和跨数据集测试，证明多模态分支真正产生增益。

### 7.2 推荐比赛基准组合

| 层级 | 数据集 | 证明能力 | 主要指标 |
|---|---|---|---|
| 主公开基准 | MIntRec2.0 | 多模态意图、多轮上下文、域外检测 | 按官方脚本报告分类与 OOS 指标 |
| 产品相关辅助基准 | ScreenSpot | 桌面/网页屏幕目标定位 | 目标点是否落入金标区域 |
| 中文辅助基准 | M3ED，是否采用取决于许可证和下载完整性 | 中文音视频上下文与缺失模态鲁棒性 | 按官方脚本报告情绪分类结果 |
| 产品封闭基准 | SoulDrive-PC-MMI | 语音 + UI + 项目上下文 + 个性化业务 | 意图、目标、槽位、冲突、澄清、延迟 |

这不是把四个数据集混成一个训练集。每个公开集保留原始标签和官方划分，使用独立任务头；只共享感知特征、对齐层或训练方法。SoulDrive 业务头只使用自建数据训练。

### 7.3 数据审计门禁

在下载和训练前，必须补齐每个候选集的：许可证、获取方式、原始音视频是否齐全、标签全集、官方划分、官方指标、基线实现、参赛权重可否再发布。当前浏览核验只确认论文摘要中的任务和规模，不代表已经通过许可证审计。

## 8. 自建数据与任务标签

`SoulDrive-PC-MMI-480` 使用 320/80/80 的训练、验证和封闭测试划分。固定的是评测材料、截图和金标，不是产品只能处理固定文本。

每个 episode 包含音频、ASR 转写、固定屏幕/UI 状态、选区、事件时间、项目、匿名画像、意图、槽位、目标、冲突、动作策略、期望回复和证据。场景模板必须跨划分隔离。

12 个业务意图保持为：选区总结、选区改写、私域问答、项目比较、待办提取、日程草案、消息/邮件草案、当前文档搜索、模板切换、确认、取消和目标澄清。

额外生成：时间错位、ASR 错误、OCR 低置信度、目标冲突、项目冲突、模态缺失和 OOS 样本。OOS 包括明确超出产品边界的桌面控制、未经确认的发送/删除以及与当前项目无关的请求。

## 9. 模型训练和推理

主模型候选调整为本地 4-bit `Qwen2.5-VL-3B-Instruct`，同时承担文字生成和慢路径屏幕视觉理解；SenseVoiceSmall 负责 ASR；RapidOCR 负责框选快路径；SoulAlign 是自训的多任务融合模型。这样主模型加三个处理小模型构成完整链路。嵌入和重排组件是否计入“三个小模型”仍须等赛题方确认；若计入，比赛推理路径先使用稀疏检索加主模型重排，避免增加第四个常驻小模型。

视觉模型是否能在 RTX 5060 8GB 上满足 P95 小于 5 秒，必须用真实屏幕分辨率实测后冻结。若慢路径不达标，先降低裁剪分辨率、复用视觉特征和减少触发频率，而不是将云端视觉作为默认方案。

训练顺序：

1. 冻结公开测试划分，复现 MIntRec2.0、ScreenSpot 候选基线；
2. 训练/迁移通用意图、对齐、OOS 与目标定位能力；
3. 用合成错位和冲突 episode 训练 SoulAlign 辅助头；
4. 用自建 320 条训练业务头，只用 80 条验证集调参；
5. 对主模型做小规模 QLoRA，输入必须是结构化决策与允许证据；
6. 最后一次运行 80 条封闭测试集并冻结结果。

关键消融：文本-only、语音+文本、语音+屏幕、去掉时间对齐、去掉项目元数据、去掉冲突门控、去掉个性化。若多模态结果没有稳定超过文本-only，不得宣称多模态创新有效。

## 10. 报告、PPT、邮件和日程的生成流程

所有大型产物采用计划式懒加载：

1. 先选择项目和证据范围；
2. 生成章节/逐页大纲及证据映射；
3. 用户确认计划；
4. 每个章节按需加载对应证据并生成；
5. 校验引用、事实、版本和缺失项；
6. 合并成产物并生成变更摘要；
7. 用户确认后导出和版本化保存。

报告不得把整库一次性塞给模型。PPT 复用现有 `presentation_service.py` 和 `openxml_presentation.py`，先补充项目证据和模板入口，不重新实现 PPTX 引擎。日程首版输出结构化草案，写入真实日历必须单独确认。

邮件采用单用户本地连接器，不建设 SoulDrive 云端业务服务器：

1. 本地联系人目录只将姓名/别名解析为邮箱地址；用户也可直接输入地址。
2. `create_email_draft` 只生成主题、正文、收件人和附件清单，不产生外部副作用。
3. 未配置连接器时导出 `.eml` 或交给默认邮件客户端；配置连接器时由本机调用邮箱服务商 SMTP/API。
4. 邮箱授权码或 OAuth 凭据保存在 Windows Credential Manager，不进入项目数据库、日志、模型上下文或知识索引。
5. `send_email` 必须接收已确认的 `draft_id`、确认令牌和幂等键；收件人、附件或正文发生变化后原确认立即失效。
6. 发送结果和失败原因仅写本地审计；失败保留草稿，不自动无限重试。

Harness 不向真实邮箱发送测试邮件。连接器测试使用本地 SMTP sink 或 mock server，验证 MIME、附件、TLS 配置、幂等和确认门控；真实服务商只做一次用户明确授权的人工验收。

## 11. 前端工作台

- 左侧：项目、来源材料、过程记录、模板和产物；
- 中央：语音入口、当前任务、预览和确认；
- 顶部：当前项目、当前窗口、选区、模型模式和隐私状态；
- 右侧：意图、目标、时间对齐、冲突、置信度和证据；
- 产物区：报告/PPT/邮件/日程的计划、生成进度、版本和导出。

框选 OCR 是无法读取系统选区时的显式降级，不是主交互。用户始终能看见本轮捕获了什么内容。

## 12. Harness 与 Runtime 基线制度

### 12.1 Baseline 的正式定义

Baseline 不是某个数据集，也不是一份公开训练集。一个有效 baseline 必须同时冻结：

- 数据集名称、版本、内容哈希和 train/validation/test 划分；
- 模型、规则管线、权重哈希、prompt 和全部推理参数；
- 代码提交标识；工作区有未提交修改时还要记录 diff 哈希；
- 随机种子、操作系统、Python/依赖、CPU/GPU 和运行模式；
- 指标实现版本、原始逐样本预测、错误类型和延迟日志。

公开训练集用于训练 baseline 模型，验证集用于选择参数，测试集用于最终比较；它们自身都不是 baseline。测试集标签在开发阶段不得进入 prompt、训练、样本生成或错误修正。

### 12.2 三层基线层级

每项新增能力都按同一层级建立比较：

1. `B0 Current`：重构前当前系统在固定工作负载上的快照，用于证明没有破坏已有能力。
2. `B1 Simple`：完成该任务所需的最简单可复现方法，例如文本-only、规则时间窗、OCR 字符串匹配或一次性 RAG。
3. `B2 Strong`：公开官方代码、公开论文基线或冻结的强模型零样本结果；只有合法可获取且本机可复现时才建立。
4. `Candidate`：本轮候选实现，必须与对应 B1/B2 使用相同数据划分、输入权限和硬件预算。

科研主张至少要求 Candidate 稳定超过 B1；若存在可复现 B2，则应与 B2 比较。工程主张还必须不低于 B0 的回归门槛。

### 12.3 各优化层的具体 baseline

| 优化层 | B0/B1 baseline | Candidate | 主要指标 |
|---|---|---|---|
| 旧有文档摄取 | 当前解析、切片和索引管线 | 增加项目/版本元数据后的管线 | 导入成功率、结构保真、耗时 |
| 项目检索 | 当前不带项目和时间过滤的混合 RAG | 项目/资产/时间过滤后再混合检索 | Recall@K、MRR/nDCG、证据覆盖、串项目率 |
| 实验比较 | 仅全文检索后由 prompt 比较 | 结构化实验目录、可比性门控和证据计算 | 实验定位、指标匹配、数值正确率、错误因果率 |
| 多模态意图 | 仅使用人工转写或 ASR 文本的分类结果 | 文本 + 音频特征 + 屏幕上下文 + SoulAlign | Macro-F1、Weighted-F1、OOS 指标、模态增益 |
| 时序对齐 | 固定时间窗内选择最近事件 | 不确定性感知事件图/SoulAlign | Alignment F1、目标绑定准确率 |
| 冲突澄清 | 将所有模态文本拼接给主模型 | 显式冲突分类与阈值澄清 | 冲突 F1、澄清准确率、危险误执行率 |
| 屏幕 grounding | OCR 可见文字匹配；公开集上加冻结 VLM 零样本结果 | UIA/OCR 快路由 + VLM 慢路由 | 金标区域命中率、拒绝准确率、延迟 |
| 个性化 | 不使用画像的通用回复 | 使用明确偏好和历史确认的回复 | 偏好命中率、内容一致率、人工成对偏好 |
| RAG 回答 | 当前一次性 RAG | 项目过滤、证据计划和分段懒加载 | 答案正确率、引用合法率、无依据陈述率 |
| 报告/PPT | 当前一次性生成或现有 PPT 服务 | 大纲/证据映射确认后的分段生成 | 事实覆盖、引用、结构完整、人工修改量 |
| Runtime | 当前文本问答固定工作负载 | 完整语音 + 屏幕 + 检索 + 回复通路 | P50/P95、首段延迟、显存、内存、失败率 |
| 隐私出端 | 当前网络与日志行为快照 | 最小化授权和本地优先策略 | 未授权出端次数、发送字段覆盖、日志泄漏 |

每层只改变一个核心因素。例如验证时间过滤时，不同时替换嵌入模型和主模型；验证 SoulAlign 时，冻结 ASR、OCR、主模型与数据划分。

### 12.4 公开数据集 baseline

公开集最终名称可等待赛题方回复，但流程现在即可冻结：

1. 保留官方 train/validation/test 划分；没有官方验证集时，从 train 按官方建议或固定种子划分，不能切分 test。
2. 第一条 baseline 是官方仓库中最接近论文表格、且能够在本机复现的方法；记录复现结果与论文结果的差距。
3. 第二条 baseline 是 text-only，证明视觉/音频到底带来多少增益。
4. 对 ScreenSpot 类视觉定位任务，再记录冻结主 VLM 的 zero-shot 结果。
5. Candidate 使用同一官方 test 和指标脚本评测；超参数只根据 validation 选择。

若赛题方没有回复，主公开基准暂按 MIntRec2.0 审计；ScreenSpot 作为产品相关辅助基准。只有许可证、原始模态、标签、划分和官方脚本全部通过审计后才下载训练并正式锁定。

### 12.5 自建集 baseline

在扩展到 480 条前，先用 30 条种子验证 schema 和 baseline 可运行性。这 30 条不是用于证明模型性能，而是发现标签和评测设计错误。

正式 `SoulDrive-PC-MMI-480` 划分冻结后：

- 文本-only baseline：只给 ASR 文本，不提供屏幕和画像；
- 规则 baseline：使用最近时间窗、显式选区和固定冲突规则；
- 无个性化 baseline：提供任务上下文但隐藏画像；
- 完整 Candidate：提供允许的全部模态、项目上下文和画像。

封闭 test 只在设计冻结后运行 baseline 和最终 Candidate。中间调优仅使用 validation。任何基于 test 失败样本的修改都必须升级数据集版本并重新建立 baseline，不能继续沿用原成绩。

### 12.6 Runtime baseline

Runtime 不只记录“总耗时”，而是使用相同的固定 episode 分解：采集、ASR、UIA/OCR/VLM、SoulAlign、检索、首 token、完整回复和产物写入。

每个场景至少运行一次冷启动和 30 次热运行，分别报告 P50、P95、最大值、失败率、CPU、内存和峰值显存。固定电源模式、模型量化、截图分辨率、上下文长度和生成 token 上限。云端调用与本地推理分开报告，不能混合平均。

Runtime 的首个 baseline 是当前文本 RAG 固定工作负载；新增模块只能占用明确的增量预算。完整多模态路径最终满足赛题五秒要求，快路径还应明显快于慢路径。

### 12.7 Harness 输出和回归门禁

每次 baseline/candidate 运行统一输出：

```text
run_manifest.json       数据、代码、模型、配置、硬件和随机种子
predictions.jsonl       每条样本的输入引用、金标和预测
metrics.json            总体、分组、置信区间和回归指标
latency.jsonl           各阶段耗时和资源占用
failures.jsonl          错误类别、证据和可复现输入
summary.md              面向人类的结论、限制与是否通过门禁
```

Harness 只负责构造输入、调用统一 `infer` 接口、记录结果和计算指标；Runtime 负责真实模型加载、路由、工具调用和响应。二者通过版本化 episode schema 解耦，禁止在评测脚本中写只对某个测试样本生效的业务规则。

任何优化开始前必须提交或保存 baseline manifest 和完整结果。没有 baseline、数据泄漏、运行条件不一致或只有汇总分没有逐样本预测时，该实验无效，不能进入报告。

## 13. 实施顺序与停止条件

### P0：冻结协议并建立现状 baseline

1. 冻结 episode schema、运行清单和 Harness 输出格式。
2. 在任何业务重构前，运行当前摄取、检索、回答、OCR、PPT 和 Runtime 工作负载，形成 `B0 Current`。
3. 当前工作区若有未提交修改，baseline manifest 同时记录 HEAD 和工作区 diff 哈希，不能只写 commit。
4. 等待赛题方五项回复；完成主候选集的标签、划分、许可证和基线审计。

验收：现状 baseline 可重复运行，逐样本结果与资源数据齐全。若公开集无法合法获取或官方基线无法复现，替换公开集，不开始业务微调。

现状 B0 优先复用已有入口：`scripts/eval_ingestion.py` 记录摄取，`scripts/eval_rag.py` 记录检索与回答，`scripts/eval_image_ocr.py` 记录 OCR，`scripts/eval_harness.py` 汇总既有 Harness。PPT 目前主要有功能测试，需用同一演示项目包补三组固定输入，分别记录现有一次性生成结果、耗时、引用和人工修改量。开始运行前先核对各脚本实际参数和输出 schema，不为凑 baseline 临时改写核心逻辑。

### P1：项目目录与时间语义

先在固定项目查询集上运行“不带项目/时间结构”的 B1，再实现项目、资产版本、实验、指标、决策、任务和产物目录；让现有索引携带项目和资产版本过滤；测试“上个月实验”的确定性查询并与 B1 比较。

### P2：选区与语音事件

先冻结 text-only 和最近时间窗规则 baseline，再实现 UI Automation 选区、框选 OCR 降级、按住说话和统一事件协议；先让规则 baseline 完成目标绑定和冲突澄清，再引入 SoulAlign。

### P3：业务闭环与 UI

先记录当前一次性 RAG/PPT 和无画像回复 baseline，再实现四类首版任务、证据预览、确认式产物和工作台。完成报告/PPT 计划式生成，邮件和日程只生成草案。

### P4：数据与训练

先生成 30 条种子验证 schema 和 baseline，再扩展到 480 条并冻结划分；实现转换、合成、训练、评测和统一 `infer.py`；复现公开/自建 baseline 后训练 SoulAlign，只有融合结果确有增益时才决定 QLoRA。

### P5：比赛交付

公开集、自建集、消融、缺失模态、OOS、P50/P95 延迟、资源占用、隐私出端检查和全新环境复现全部通过后，才制作最终答辩材料。

停止条件：公开集低于可比基线、多模态不优于文本-only、自建封闭集泄漏、P95 超过 5 秒、模型数量不合规或无法复现时，不扩展摄像头、U 盘和更多桌面控制，优先修复主链路。

## 14. 待赛题方回复后才能冻结的决策

- 公开测试集究竟由谁选择及自动评测如何执行；
- 屏幕/UI 是否属于内部集认可的视觉上下文；
- 内部集任务和主要输出指标；
- 三个小模型的计数口径；
- 五秒延迟的起止点和硬件。

收到回复后先更新本文和数据集审计，不直接修改模型代码。
