# 全局 Skill 删除的请求范围与对象范围分离

日期：2026-10-08。状态：B0 已复现，候选定向与第四轮完整检查通过。

## 缺口与业务边界

项目窗口可使用全局 Skill，删除接口也显式允许 `include_global=True`。但是删除收据仅保存对象的 `project_id`；入口重试校验却拿它与请求的 `project_id` 比较。从项目 A 删除全局 Skill，第一次成功，原请求重试却返回 409；完成收据写入失败后的恢复也同样受阻。

本轮假设保持既有产品权限：全局 Skill 在项目窗口可删除，不新增删除入口或扩大权限。只分离“请求来自哪个项目”和“目标 Skill 属于哪个范围”，源目录验证继续使用对象范围，幂等身份继续严格绑定原请求。所有删除/故障注入测试仅作用于临时工作区，不删除用户 Skill。

## 外部机制与最小方案

参考 [Restate HTTP idempotency](https://docs.restate.dev/services/invocation/http) 的稳定调用身份、完成结果回放与安全重试，以及 [Temporal Activity Definition](https://docs.temporal.io/activity-definition) 的可重试副作用边界。本项目沿用现有 SQLite 阶段收据，不引入外部 durable runtime。

验收：

- 新收据分别保存请求项目与目标项目，输入摘要绑定两者。
- 同键、同请求项目能回放成功，并能从 `source_removed` 恢复。
- 换请求项目或去掉原请求项目仍返回 409，不能把全局对象放宽为任意项目共享幂等键。
- 旧收据不捏造缺失的请求身份。项目对象的旧收据可以在范围确实可确定时兼容；全局对象旧收据的发起范围不明，必须拒绝自动继续并提示人工确认。
- 增量迁移不删除既有收据、Skill 或记忆，也不更改已冻结评测集。

## 候选与定向结果

- `skill_deletion_receipts` 增量增加 `requested_project_id`。已知无项目请求存空字符串，旧收据迁移后保留 NULL 表示未知，避免把未记录身份伪装成已知无项目。
- 新输入摘要同时绑定请求范围和目标范围；入口回放校验请求范围，目录清理继续使用目标范围。
- 旧项目对象收据只允许同项目、原输入摘要验证后接管，并升级摘要；旧全局对象收据无法确定发起项目，入口和存储层均拒绝自动执行，保留收据并提示人工确认。
