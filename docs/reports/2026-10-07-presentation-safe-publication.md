# PPT 产物无覆盖发布与内容级恢复

开始日期：2026-10-07；记录更新：2026-10-08。状态：候选已完成第一轮全量工程回归。

## 范围与验收条件

对应执行大纲 E4/E5：恢复只接受属于同一任务、同一实际大纲、同一步骤且内容未改变的产物；未知、旧版无内容指纹或用户编辑过的文件必须保留，不能自动覆盖。渲染与最终发布之间中断时，重试应从已校验的暂存文件继续，不重渲染。

所有反例只使用临时工作区、虚构任务和两页 PPT。没有修改冻结业务评测数据、统计语义或用户资料。该确定性缺陷不需要新模型或强基线框架，B1 为最小安全文件发布机制，B2 不另行部署。

## 外部机制与本地取舍

- [DBOS Steps](https://docs.dbos.dev/python/tutorials/step-tutorial)：文件访问属于需持久化结果的非确定性操作；复用本地 TaskJournal 和收据，不增加运行平台。
- [DBOS Transactional Outbox](https://docs.dbos.dev/python/examples/outbox)：外部副作用可能至少执行一次，需由副作用端处理幂等。SoulDrive 将“渲染内部暂存文件”和“发布用户可见文件”分开。
- [Restate Durable Steps](https://docs.restate.dev/develop/python/durable-steps)：恢复依赖已记录的操作结果。采用已校验内容的 SHA-256 收据，不把“写过 rendering 标记”当成产物已经完成的证明。

以上是机制参考，不证明本项目采用后自动有效；有效性由下面的本机反例和回归判定。

## B0 修复前实测

新增六个反例后、修改生产逻辑前执行定向测试：**6 failed，41 deselected，0.47 秒**。

1. 无收据的已有文件没有被拒绝，旧逻辑允许重新渲染覆盖。
2. `rendering` 标记加上结构合法/同页数文件被当成可恢复，即使无内容完成证明。
3. 用户修改的合法 PPTX 仍被当成原计划产物恢复。
4. 已校验暂存文件无法在发布中断后继续，因为旧逻辑直接生成到最终路径。
5. 发布前目标文件出现的竞争窗口没有无覆盖发布门。
6. 不同完整 task ID 只要末尾八字符相同，就生成相同文件名。

运行环境：Windows 本机、Conda `souldrive`、UTF-8；该轮无模型推理、网络发送或真实 WPS 调用。测试耗时仅是上述工程反例耗时，不是业务响应性能。

## 候选与验证记录

此前的 2026-09-15 marker 报告是历史记录；其结构校验级恢复边界不等于本轮内容级恢复标准。

候选保留现有任务服务，OpenXML 和 WPS/COM 共用发布边界：

1. 每次 renderer 只写本轮独有的内部暂存文件，不直接写最终路径。
2. 校验 PPTX，刷新暂存文件，计算 SHA-256，并先持久化 `ready` 收据。
3. 在同一文件系统使用 `os.link` 原子建立最终路径；目标已经存在时明确拒绝，绝不退回覆盖式写入。
4. 写入 `completed` 收据后移除本轮暂存链接。文件已发布但最后收据丢失时，可按 `ready` 的内容指纹恢复。
5. 恢复同时核对实际大纲摘要、完整任务身份、步骤幂等键、页数、结构与文件内容指纹。用户改过的合法 PPTX 不再被误认成原计划输出。
6. 文件名取完整 task ID 的 SHA-256 前 16 位，避免原先末尾八字符相同的确定性碰撞。旧版同任务产物有匹配身份收据但缺少内容指纹时，保留文件并要求新计划/新确认，不静默复制或覆盖。

验证：六个初始反例修复后通过；旧版兼容、暂存内容改变和 COM 测试替身等补充后，PPT/TaskJournal/论文接口组合 **96 passed，1 warning，10.82 秒**。COM 只验证参数与共享发布路径，不是实际 WPS 测试。

第一轮完整 `scripts/check.ps1`：后端 **1672 passed，1 warning，466.80 秒**；前端生产构建、8 组脚本测试合计 **66 passed**；`compileall` 和 `cargo check --locked` 通过，整轮退出码 `0`。该轮测试收集后新增的记忆 CLI 失败门反例不包含在 1672 项中；后续第二轮聚合回归单独记录，不能混算。

实现中实测发现 Windows 对只读句柄 `fsync` 返回 bad file descriptor，已改为只对本轮暂存文件以 `rb+` 打开并刷新；修复后上述正向发布和恢复均通过。
